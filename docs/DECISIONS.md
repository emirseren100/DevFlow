| 26 | SHA-256 â€” and only SHA-256 â€” for session-token storage (Phase 3) | The token is already 32 cryptographically random bytes, so there is nothing to guess; hashing it just makes a stolen database dump useless. | 30 | Server-generated slug that never changes after creation (Phase 4) | A slug belongs in URLs, so the user should not have to invent one, and it must be unique globally â€” the server derives it from the name and adds a numeric suffix on collision. | 31 | Membership rows are the only way in; ownership alone grants nothing (Phase 4) | One rule to check on every request â€” "is there a `WorkspaceMember` row for this user?" â€” instead of "member **or** owner" scattered through the code. | 32 | Exactly one permanent OWNER per workspace, and no ownership transfer yet (Phase 4) | Every workspace always has one account that can delete it and manage admins; forbidding a second OWNER and forbidding self-demotion makes an orphaned workspace impossible. | 33 | Members are existing registered users, added by email â€” no invitations (Phase 4) | Invitations need an email provider, pending-invite state, tokens and expiry. | 34 | Roles are read from the database on every request (Phase 4) | The client is not a trusted source: a role in the body, a header or React state can be edited by anyone with dev tools. | 35 | Client permission helpers hide controls, they do not protect anything (Phase 4) | Showing a member a "Delete workspace" button that always fails is bad UX, so the client mirrors the rules. | 36 | React Query deferred (Phase 4) | Two screens with one or two requests each are served fine by `useEffect` and `useState`; adding a cache layer now would mean cache keys, invalidation rules and a new dependency to explain before there is any duplicated fetching to solve. | 37 | Project keys are immutable after creation (Phase 5) | Every issue is referred to as `API-14` in chats, commits and bookmarks; letting the key change would silently rewrite every one of those references. | 38 | Issue numbers are scoped per project, not global (Phase 5) | `API-1` and `WEB-1` both exist, so each team reads short numbers that mean something inside their own project. | 39 | The issue number comes from a transactional counter, not `count + 1` (Phase 5) | Incrementing `project.nextIssueNumber` inside the creating transaction locks the project row, so two simultaneous requests get two different numbers. | 41 | A sprint may only hold issues of its own project (Phase 5) | A sprint plans one project's work; a cross-project link would make sprint counts and future board views meaningless. | 42 | Server-side pagination for the issue list (Phase 5) | Issue lists grow without bound; sending all of them and filtering in the browser would make the response size a function of project age. `page`, `limit` (100 maximum), `sort` and `order` are validated and applied in PostgreSQL, and the response carries the pagination metadata the UI needs | Client-side filtering of the full list, infinite scroll (needs cursors and more UI than this phase has) |
| 43 | Comments, the activity feed and the Kanban board deferred to Phase 6 (Phase 5) | Phase 5 is already the largest surface in the project: three resources, their authorization and their client pages. | 44 | React Query still deferred (Phase 5) | The new pages fetch two or three endpoints on mount and refetch when the URL query changes; the URL, not a cache, is the source of truth for the issue filters. | 45 | Comments are plain text (Phase 6) | The body is trimmed, length-checked and rendered as text with `white-space: pre-wrap`, so line breaks survive and any HTML a user types stays visible characters. | 46 | Comments and activity stay two separate models (Phase 6) | A comment is something a person wrote and may edit or delete; an activity row is what the system recorded and nobody may edit. | 47 | Activity sentences are generated in the client (Phase 6) | The database stores a type plus small structured metadata (`previousStatus`, `nextStatus`, `changedFields`, `commentId`), so wording, translation and formatting can change without a migration and without rewriting history | Storing a formatted English sentence per row (frozen wording, impossible to translate, and a migration for every copy change) |
| 48 | Activity metadata is sanitized against a whitelist on the way out (Phase 6) | A feed is the easiest place to leak something by accident. Only known small keys leave the server, so a future careless writer cannot expose a token, a full issue or a whole user object through the feed | Returning `metadata` as stored, a blacklist of forbidden keys (anything new is exposed by default) |
| 49 | `Issue.position` is a column-local integer, renumbered on every move (Phase 6) | Positions are `0, 1, 2, â€¦` inside one status column, which is trivial to read, to test and to explain: "the third card in To Do". | 50 | The server owns the final ordering (Phase 6) | The client sends only `issueId`, `targetStatus` and `targetIndex`. The server reads the real order from PostgreSQL and writes the result, so a hand-made request cannot reorder other people's cards, and the response is the confirmed board | Accepting the client's full list of issue ids (a trusted client is not a thing), one request per changed card (a partial failure leaves a broken order) |
| 51 | A move is one serializable transaction with a bounded retry (Phase 6) | A move touches several rows in two columns; a half-applied move would leave duplicate positions. `Serializable` makes two concurrent reorders of the same column impossible to interleave, and a small retry on Prisma's `P2034` handles the conflict this causes | Read-then-write without a transaction (a real race), row locks by hand, a distributed lock or Redis (infrastructure for a problem one transaction already solves) |
| 52 | `@dnd-kit` for drag-and-drop (Phase 6) | Small, React-native (no wrapper around a DOM library), keyboard sensors included, and no styling opinion. | 53 | Every card also has a non-drag move control (Phase 6) | Dragging cannot be the only way to change a status: it excludes keyboard-only and screen-reader users, and it is awkward on touch. | 54 | Optimistic move with a real rollback, not a spinner (Phase 6) | The board moves the card immediately, then replaces the whole board with the server's answer. On failure the saved board comes back and the error is shown, so a rejected move can never leave a duplicated or missing card | Waiting for the server before moving anything (feels broken while dragging), optimistic update without rollback (the UI keeps a move the server refused) |
| 55 | Realtime updates and WebSockets deferred (Phase 6) | A team of this size can reload. A socket layer means a second server protocol, connection state, reconnection, per-workspace authorization on every message and a much harder test story â€” for a feature the MVP does not need | WebSockets or Server-Sent Events now, polling the board on a timer (constant load for rare changes) |
| 56 | TanStack Query is the one server-state layer (Phase 7) | Seven screens now read the same workspaces, projects and issues. `useEffect` + `useState` per page meant a refetch per mount, a hand-written loading and error branch per page, and no way to refresh the right screens after a mutation. | 57 | `AuthProvider` keeps the authentication lifecycle (Phase 7) | Who is signed in is not ordinary cached data: it decides routing, it must be cleared instantly on a `401`, and login and logout are explicit lifecycle events rather than a stale-time. | 58 | Centralized query-key factories, no keys written inline (Phase 7) | Invalidation is only correct if two places agree on the exact key. One file gives every key one definition, makes the prefix relationships visible, and turns a typo into a compile error instead of a screen that silently never refreshes | Inline key arrays per component (drift, silent stale screens), a string-based key convention (no type safety) |
| 59 | No automatic query retry; a visible "Try again" instead (Phase 7) | `401`, `403` and `404` are correct answers, not flakiness — retrying them hides the reason and delays the error screen. Letting the user retry is honest, keeps tests deterministic and never produces a burst of doomed requests | Retrying everything a few times (slow, confusing errors, noisy tests), retrying only 5xx (extra rule for a case a button already covers) |
| 60 | One workspace dashboard endpoint instead of many small requests (Phase 7) | The overview needs eleven numbers, two distributions and two short lists. Six client requests would arrive at six moments and describe six different states; one aggregation answers a consistent snapshot, computed with `count`/`groupBy` in PostgreSQL and without sending a single issue description | Composing the dashboard from the existing list endpoints (inconsistent snapshot, N+1 over the network), counting in the browser (downloads every issue), a materialized summary table (a second copy to keep in sync) |
| 61 | Overdue is decided by the server clock (Phase 7) | The comparison `dueDate < now` must mean the same thing for everybody. A date sent by the browser can be wrong or forged, so the count would differ per machine. The server returns `generatedAt` with the response, and the client only formats timestamps for display | Comparing in the browser (per-machine truth, trivially forged), storing a timezone per user (a feature nobody asked for), adding a timezone library (ISO strings and `toLocaleString` are enough) |
| 62 | No UI component library and no charting package (Phase 7) | Five status counts are five rows with a CSS bar. | 63 | Shared loading, empty and error states instead of blank screens (Phase 7) | Every server-backed screen has the same four outcomes. | 64 | No last-selected workspace stored in the browser (Phase 7) | The URL already says which workspace is open, and it survives a reload and a shared link. | 65 | Final visual design still deferred to Phase 9 (Phase 7) | Phase 7 is about structure: which page exists, where data comes from, and how loading, permission and error states behave. | 66 | Helmet for HTTP security headers, with CSP switched off here (Phase 8) | One well-maintained middleware sets the headers a JSON API should send and removes `X-Powered-By`. | 67 | Rate limiting only on login and register (Phase 8) | Those two endpoints are the ones worth guessing at, and they are cheap to hammer. | 68 | The rate-limit response is identical for a known and an unknown email (Phase 8) | The login error already refuses to say which of the email and the password was wrong; a limiter that behaved differently for real accounts would hand that information straight back. | 69 | An allowed-origin check on state-changing requests, not a CSRF-token framework (Phase 8) | The browser attaches the session cookie whatever page started the request. `SameSite=Lax` and CORS both help, but neither is a server-side check. | 70 | A missing `Origin` is accepted outside production (Phase 8) | Browsers always send `Origin` on `POST`, `PUT`, `PATCH` and `DELETE`, so a forged cross-site request cannot omit it. | 71 | A 100kb JSON body limit (Phase 8) | An unbounded body is a free denial-of-service: anyone can stream gigabytes into the process. 100kb is ten times the largest description the schema allows, so no legitimate request is affected, and the refusal is a clean `413 PAYLOAD_TOO_LARGE` rather than an anonymous 500 | No limit (trivial memory exhaustion), a limit so tight that a long issue description fails (breaks a real feature), a per-route limit (more configuration for one number) |
| 72 | Multi-stage Docker builds (Phase 8) | The build needs TypeScript, the Prisma CLI and every devDependency; the running server needs none of them. | 73 | The Prisma CLI is a normal dependency, not a devDependency (Phase 8) | The container runs `prisma migrate deploy` at start, so the CLI has to survive `npm ci --omit=dev`. Moving it is a classification change, not an upgrade, and it costs nothing locally because it was already installed | Keeping it in devDependencies and installing the whole tree in the runtime image (defeats the multi-stage split), migrating from outside the container (an extra manual step before every start) |
| 74 | Docker client on host port 5175, PostgreSQL on host port 5433 (Phase 8) | The Docker stack has to be startable while `npm run dev` is already running, and on a machine that may already have PostgreSQL installed. Different host ports make both possible; inside the Compose network the services still use the ordinary 80 and 5432 | Reusing 5174 and 5432 (the stack refuses to start next to a local setup), random ports (nothing to document or remember) |
| 75 | `prisma migrate deploy` in containers and CI, never `migrate dev` (Phase 8) | `deploy` only replays committed migrations: it never authors one, never prompts and never resets a database. `migrate dev` can do all three, which is right on a laptop and catastrophic in an automated environment | `migrate dev` in the container (can reset real data), `db push` (skips the migration history entirely, so CI would never verify that the committed migrations actually apply) |
| 76 | A PostgreSQL service container in CI instead of mocks (Phase 8) | The tests exist to prove unique constraints, cascades, transactions and role checks work in PostgreSQL. A service container is disposable, created per run, and its credentials never leave the runner — so no repository secret is needed | Mocking Prisma (tests the mock, not the schema), SQLite in CI (different SQL, different constraint behaviour), a shared cloud test database (slow, and two runs would fight over the same rows) |
| 77 | The development seed never runs automatically (Phase 8) | The seed creates named accounts with one shared, publicly documented password. That is exactly right on a laptop and a serious hole anywhere else, so no container start and no CI step invokes it; the integration tests build their own fixtures instead | Seeding on container start (ships known credentials), seeding in CI (tests would then depend on seed data and on each other) |
| 78 | Deployment deferred to Phase 9 (Phase 8) | Phase 8 makes the project *deployable*: validated configuration, security middleware, reproducible images and a pipeline that proves the whole thing builds. | 79 | One hand-written CSS token file instead of a UI framework or utility CSS (Phase 9A) | The application is a shell, a form, a list, a badge and a dialog. Twenty custom properties and about six hundred lines of plain CSS cover all of it, stay readable to an intern, and add nothing to the bundle beyond the 4 kB of gzipped CSS actually used. A component library would have decided the identity that this phase exists to decide, and would have to be fought whenever it disagreed | Material UI / Chakra / shadcn (a whole design system and its opinions for five kinds of block), Tailwind (a build step and class soup in the markup for a project with one theme), CSS-in-JS (runtime cost and a second styling language) |
