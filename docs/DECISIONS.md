| # | Decision | Why | Rejected alternatives |

| 1 | React + TypeScript for the frontend | Largest ecosystem and the most common stack in job postings; TypeScript catches shape errors at compile time and makes API contracts explicit | Vue/Angular/Svelte (smaller hiring surface for this portfolio), plain JavaScript (no compile-time safety) |
| 2 | Vite as the frontend build tool | Fast dev server, native ESM, first-class TypeScript, near-zero configuration | Create React App (unmaintained), Webpack by hand (config burden), Next.js (adds SSR and a framework backend this project does not need) |
| 3 | React Router for client routing | Standard library for SPA routing; nested routes match the workspace â†’ project â†’ issue hierarchy | TanStack Router (less common), hand-rolled routing (reinventing a solved problem) |
| 4 | Express for the backend | Minimal, well-documented, understandable end-to-end; middleware model is easy to explain in an interview | NestJS (decorator/DI weight for a small app), Fastify (fine, but smaller learning material), serverless functions (harder local story) |
| 5 | PostgreSQL as the database | Relational data with real foreign keys â€” users, workspaces, projects, issues, comments are inherently relational; strong constraints and indexing | MongoDB (relations by hand, weaker integrity guarantees), SQLite (not representative of production hosting) |
| 6 | Prisma as the ORM | Type-safe generated client, readable schema file, versioned migrations committed to git | Raw SQL (no type safety, manual migrations), TypeORM/Sequelize (heavier, weaker TypeScript inference), Drizzle (good, but Prisma has more learning material) |
| 7 | Zod for validation | One schema produces both runtime validation and the static TypeScript type via `z.infer`; no duplicated definitions | Joi/Yup (no type inference), manual `if` checks (error-prone, inconsistent messages), `class-validator` (needs decorators and DI) |
| 8 | HTTP-only cookie session authentication | Cookie is unreadable by page JavaScript, which removes the XSS token-theft risk of `localStorage`; the browser attaches it automatically | JWT in `localStorage` (XSS-exposed), JWT in an `Authorization` header (same storage problem), third-party auth provider (hides the mechanism this project exists to learn) |
| 9 | `client/` and `server/` folder split in one repository | One repo to clone, run and review; clear boundary between browser code and server code without monorepo tooling | Two separate repositories (painful to run together), single mixed folder (no boundary), Nx/Turborepo monorepo (tooling overhead for two packages) |
| 10 | REST API | Predictable resource URLs, plain HTTP verbs and status codes, trivial to test with Supertest and inspect in the browser network tab | GraphQL (schema/resolver/caching overhead for a small fixed client), tRPC (couples client and server, less transferable as an API skill) |
| 11 | Docker Compose for local infrastructure | One command brings up PostgreSQL with a persistent volume; no host database install, identical setup for any reviewer | Locally installed PostgreSQL (setup friction per machine), hosted cloud database in development (cost, network dependency), Kubernetes (absurd for this scale) |
| 12 | npm as the package manager | Ships with Node.js, zero setup for a reviewer cloning the repo | pnpm/yarn/bun (faster, but an extra install step for anyone evaluating the project) |
| 13 | Vitest + React Testing Library + Supertest for tests | Vitest shares the Vite config and runs both sides; RTL tests user-visible behaviour; Supertest exercises the real Express app | Jest (extra config for TypeScript/ESM), Cypress/Playwright as the primary layer (slow, added later if at all) |
| 14 | Monolith, not microservices | A single team-sized product with one database; splitting services would add network calls, deployment complexity and distributed failure modes for no gain | Microservices, event-driven architecture, hexagonal/clean-architecture layering |
| 15 | Real PostgreSQL instead of an in-memory or file database (Phase 2) | The product depends on foreign keys, enums, composite unique constraints and indexes; an in-memory store would fake all of them and hide bugs until production | SQLite (different SQL dialect and constraint behaviour), in-memory mock data (no integrity guarantees at all) |
| 16 | Prisma 7 with the `@prisma/adapter-pg` driver adapter (Phase 2) | Prisma 7 connects through a driver adapter instead of a bundled engine; `pg` is the standard PostgreSQL driver, and `prisma.config.ts` keeps schema, migrations and seed configuration in one typed file | Prisma 6 configuration style (mixing v6 and v7 patterns breaks the CLI), a query builder or raw SQL (loses generated types and migrations) |
| 17 | Versioned migrations, not `db push` (Phase 2) | Migration SQL files are committed, so every machine and environment reaches the same schema through the same reviewable steps; `db push` silently mutates a database and leaves no history | `prisma db push` as the main workflow, hand-written SQL applied manually |
| 18 | Explicit `WorkspaceMember` join model instead of an implicit many-to-many (Phase 2) | Membership carries data of its own â€” `role` and `joinedAt` â€” and Phase 3 authorization reads it on every request; an implicit relation table cannot hold those columns | Implicit Prisma many-to-many, a role array on `User` (cannot differ per workspace) |
| 19 | Database enums for role, status, type and priority (Phase 2) | PostgreSQL rejects invalid values at the database level and Prisma generates matching TypeScript unions, so one definition covers both layers | Free-text strings validated only in application code, integer codes (unreadable in the database) |
| 20 | Optional `assigneeId` and `sprintId` on `Issue` (Phase 2) | An issue genuinely exists before anyone owns it or plans it into a sprint; forcing values would mean inventing placeholder rows. Deleting a sprint sets the link to null instead of deleting real work | Required assignee/sprint, a synthetic "unassigned" user and "backlog" sprint record |
| 21 | Authentication credentials deferred to Phase 3 (Phase 2) | Password hashing and session storage are security-sensitive and belong with the endpoints that use them; storing credential columns before any code reads them invites half-finished auth | Adding `passwordHash` and session tables now "to save a migration" |
| 22 | Ordinary unit and API tests do not use the development database (Phase 2) | Tests must pass on a clean checkout with no PostgreSQL running, and they must never mutate a developer's data; database confidence in this phase comes from schema validation, migration status, the seed and the read-only `db:check` script | Pointing the test suite at the development database, spinning up a throwaway database per test run (deferred to Phase 8) |
| 23 | Database-backed sessions instead of JWT (Phase 3) | A session row can be revoked instantly â€” logout, or an admin killing a session, takes effect on the next request; a signed JWT stays valid until it expires. The lookup is one indexed query and the app already has PostgreSQL | JWT access tokens, access/refresh token pairs (extra machinery to work around the revocation problem JWT creates) |
| 24 | HTTP-only cookie instead of a token in `localStorage` (Phase 3) | Page JavaScript cannot read an `httpOnly` cookie, so an XSS bug cannot steal the session; the browser also attaches it automatically, so no client code handles secrets | Token in `localStorage`/`sessionStorage` (readable by any injected script), `Authorization` header with a stored token (same storage problem) |
| 25 | Argon2id for password hashing (Phase 3) | Winner of the Password Hashing Competition and the current OWASP default; the `id` variant resists both GPU and side-channel attacks, and the cost parameters make guessing expensive. Used through `@node-rs/argon2`, which ships prebuilt binaries and needs no compiler on Windows | bcrypt (older, 72-byte input limit), scrypt (fine but less recommended today), SHA-256 or a hand-rolled scheme (far too fast to resist guessing) |
| 26 | SHA-256 â€” and only SHA-256 â€” for session-token storage (Phase 3) | The token is already 32 cryptographically random bytes, so there is nothing to guess; hashing it just makes a stolen database dump useless. A slow hash here would add latency to every single request for no security gain | Argon2 for session tokens (slow on every request), storing raw tokens (a database leak becomes an account takeover) |
| 27 | `PasswordCredential` as a separate one-to-one model (Phase 3) | Authentication secrets stay out of the profile table, so an ordinary `user.findMany()` cannot leak a hash, and a nullable `passwordHash` column that "should always be set" never exists | A nullable `passwordHash` column on `User` (simpler migration, but the hash then travels with every user query) |
| 28 | A dedicated test database, guarded by a name check (Phase 3) | Authentication tests must create and delete rows; a real database is the only way to test unique constraints, cascades and expiry. The setup refuses any `DATABASE_URL` that does not contain `devflow_test`, so a mistyped URL cannot wipe development data | Running tests against the development database, mocking Prisma (would test the mock, not the schema), an in-memory database (different SQL behaviour) |
| 29 | OAuth, password reset, email verification and MFA deferred (Phase 3) | Each needs an email provider or a third-party integration and would triple the surface of this phase; the goal here is to understand and own the core session mechanism. They are documented as known limitations rather than silently missing | Adding a third-party auth provider (hides the mechanism this project exists to learn), building password reset without an email service (untestable) |
| 30 | Server-generated slug that never changes after creation (Phase 4) | A slug belongs in URLs, so the user should not have to invent one, and it must be unique globally â€” the server derives it from the name and adds a numeric suffix on collision. Renaming keeps the old slug, so links and bookmarks that already exist stay valid | A user-chosen slug (extra field, extra validation, taken-name errors), regenerating the slug on every rename (silently breaks existing links) |
| 31 | Membership rows are the only way in; ownership alone grants nothing (Phase 4) | One rule to check on every request â€” "is there a `WorkspaceMember` row for this user?" â€” instead of "member **or** owner" scattered through the code. The creator therefore gets an `OWNER` membership row in the same transaction as the workspace | Treating `Workspace.ownerId` as an implicit membership (two access paths to keep in sync), a second membership model for owners |
| 32 | Exactly one permanent OWNER per workspace, and no ownership transfer yet (Phase 4) | Every workspace always has one account that can delete it and manage admins; forbidding a second OWNER and forbidding self-demotion makes an orphaned workspace impossible. Transfer needs its own confirmation flow and is not required by any Phase 4 use case | Multiple owners (unclear who is ultimately responsible), transferable ownership now (extra flow, extra failure modes), no owner concept at all |
| 33 | Members are existing registered users, added by email â€” no invitations (Phase 4) | Invitations need an email provider, pending-invite state, tokens and expiry. Looking up an existing account keeps the membership model to one table and returns an honest `404 USER_NOT_FOUND` instead of an invisible pending row | Email invitations with tokens (needs an email service, untestable locally), auto-creating an account for an unknown email (creates accounts nobody asked for) |
| 34 | Roles are read from the database on every request (Phase 4) | The client is not a trusted source: a role in the body, a header or React state can be edited by anyone with dev tools. One query loads the workspace and the caller's membership together, so the check costs one round trip | Sending the role from the client, caching the role in the session cookie (goes stale when a role changes and can be tampered with) |
| 35 | Client permission helpers hide controls, they do not protect anything (Phase 4) | Showing a member a "Delete workspace" button that always fails is bad UX, so the client mirrors the rules. The server re-checks every request, because hiding a button changes nothing for a hand-written `curl` call | Trusting the UI to enforce permissions, rendering every control for everyone |
| 36 | React Query deferred (Phase 4) | Two screens with one or two requests each are served fine by `useEffect` and `useState`; adding a cache layer now would mean cache keys, invalidation rules and a new dependency to explain before there is any duplicated fetching to solve. Revisit when several screens share the same server data | Adding React Query now (premature), writing a custom caching layer (all of the cost, none of the ecosystem) |
| 37 | Project keys are immutable after creation (Phase 5) | Every issue is referred to as `API-14` in chats, commits and bookmarks; letting the key change would silently rewrite every one of those references. The name and description stay editable, so nothing readable is frozen | Editable keys with a rewrite of every reference (impossible outside the app), a stored full display key per issue (a second copy that can drift) |
| 38 | Issue numbers are scoped per project, not global (Phase 5) | `API-1` and `WEB-1` both exist, so each team reads short numbers that mean something inside their own project. A global sequence would make the first issue of a new project number 4297 | One global counter (meaningless large numbers), the database id in the UI (a cuid is unreadable) |
| 39 | The issue number comes from a transactional counter, not `count + 1` (Phase 5) | Incrementing `project.nextIssueNumber` inside the creating transaction locks the project row, so two simultaneous requests get two different numbers. Counting rows first lets both read the same total and write the same number; a unique index on `(projectId, number)` backs the rule up in the database | `count + 1` or `max(number) + 1` outside a transaction (a real race), a database sequence per project (one sequence object per project to create and drop) |
| 40 | An assignee must be a current workspace member (Phase 5) | Assignment is a permission statement: the assignee may edit the issue. Accepting any registered user id would hand edit rights to somebody outside the workspace, so the membership row is checked before the write and an unrelated id returns `400 INVALID_ASSIGNEE` | Trusting the client to send a valid id, checking only that the user exists |
| 41 | A sprint may only hold issues of its own project (Phase 5) | A sprint plans one project's work; a cross-project link would make sprint counts and future board views meaningless. The sprint is looked up with its `projectId` in the filter, so a foreign id returns `400 INVALID_SPRINT` | Workspace-wide sprints (a bigger model than the MVP needs), no validation at all |
| 42 | Server-side pagination for the issue list (Phase 5) | Issue lists grow without bound; sending all of them and filtering in the browser would make the response size a function of project age. `page`, `limit` (100 maximum), `sort` and `order` are validated and applied in PostgreSQL, and the response carries the pagination metadata the UI needs | Client-side filtering of the full list, infinite scroll (needs cursors and more UI than this phase has) |
| 43 | Comments, the activity feed and the Kanban board deferred to Phase 6 (Phase 5) | Phase 5 is already the largest surface in the project: three resources, their authorization and their client pages. Activity rows are written now (`PROJECT_CREATED`, `ISSUE_CREATED`, `ISSUE_UPDATED`, `ISSUE_STATUS_CHANGED`, `ISSUE_ASSIGNED`) so Phase 6 has data to read, but nothing reads them yet | Building comments and a board in the same phase (a much bigger change to review at once) |
| 44 | React Query still deferred (Phase 5) | The new pages fetch two or three endpoints on mount and refetch when the URL query changes; the URL, not a cache, is the source of truth for the issue filters. There is still no duplicated server state between screens to justify a cache layer | Adding React Query now (premature), a hand-rolled cache (all of the cost, none of the ecosystem) |
| 45 | Comments are plain text (Phase 6) | The body is trimmed, length-checked and rendered as text with `white-space: pre-wrap`, so line breaks survive and any HTML a user types stays visible characters. Markdown or rich text would add a parser, a sanitizer and an XSS surface for a feature nobody asked for | A Markdown editor with sanitization, a rich-text editor storing HTML, mentions and reactions |
| 46 | Comments and activity stay two separate models (Phase 6) | A comment is something a person wrote and may edit or delete; an activity row is what the system recorded and nobody may edit. Merging them into one "timeline" table would mean one model with two sets of permissions and a nullable body | One timeline model with a `kind` column, storing comments as activity rows with metadata |
| 47 | Activity sentences are generated in the client (Phase 6) | The database stores a type plus small structured metadata (`previousStatus`, `nextStatus`, `changedFields`, `commentId`), so wording, translation and formatting can change without a migration and without rewriting history | Storing a formatted English sentence per row (frozen wording, impossible to translate, and a migration for every copy change) |
| 48 | Activity metadata is sanitized against a whitelist on the way out (Phase 6) | A feed is the easiest place to leak something by accident. Only known small keys leave the server, so a future careless writer cannot expose a token, a full issue or a whole user object through the feed | Returning `metadata` as stored, a blacklist of forbidden keys (anything new is exposed by default) |
| 49 | `Issue.position` is a column-local integer, renumbered on every move (Phase 6) | Positions are `0, 1, 2, â€¦` inside one status column, which is trivial to read, to test and to explain: "the third card in To Do". Renumbering the affected columns keeps them contiguous, so no gap or duplicate can accumulate | Fractional or gap positions (`1000, 2000`, needs periodic compaction), a linked list of `previousIssueId` (one broken link corrupts a column), sorting by `updatedAt` (no manual ordering at all) |
| 50 | The server owns the final ordering (Phase 6) | The client sends only `issueId`, `targetStatus` and `targetIndex`. The server reads the real order from PostgreSQL and writes the result, so a hand-made request cannot reorder other people's cards, and the response is the confirmed board | Accepting the client's full list of issue ids (a trusted client is not a thing), one request per changed card (a partial failure leaves a broken order) |
| 51 | A move is one serializable transaction with a bounded retry (Phase 6) | A move touches several rows in two columns; a half-applied move would leave duplicate positions. `Serializable` makes two concurrent reorders of the same column impossible to interleave, and a small retry on Prisma's `P2034` handles the conflict this causes | Read-then-write without a transaction (a real race), row locks by hand, a distributed lock or Redis (infrastructure for a problem one transaction already solves) |
| 52 | `@dnd-kit` for drag-and-drop (Phase 6) | Small, React-native (no wrapper around a DOM library), keyboard sensors included, and no styling opinion. HTML5 drag-and-drop by hand has poor touch support and no keyboard story | `react-beautiful-dnd` (no longer maintained), raw HTML5 drag events (fragile, inaccessible), a full UI framework with a board component (a whole design system for one screen) |
| 53 | Every card also has a non-drag move control (Phase 6) | Dragging cannot be the only way to change a status: it excludes keyboard-only and screen-reader users, and it is awkward on touch. A labelled "Move â€¦ to" select does the same thing through one plain request | Drag-only interaction, a separate "accessible mode" (two code paths to keep in sync) |
| 54 | Optimistic move with a real rollback, not a spinner (Phase 6) | The board moves the card immediately, then replaces the whole board with the server's answer. On failure the saved board comes back and the error is shown, so a rejected move can never leave a duplicated or missing card | Waiting for the server before moving anything (feels broken while dragging), optimistic update without rollback (the UI keeps a move the server refused) |
| 55 | Realtime updates and WebSockets deferred (Phase 6) | A team of this size can reload. A socket layer means a second server protocol, connection state, reconnection, per-workspace authorization on every message and a much harder test story â€” for a feature the MVP does not need | WebSockets or Server-Sent Events now, polling the board on a timer (constant load for rare changes) |
| 56 | TanStack Query is the one server-state layer (Phase 7) | Seven screens now read the same workspaces, projects and issues. `useEffect` + `useState` per page meant a refetch per mount, a hand-written loading and error branch per page, and no way to refresh the right screens after a mutation. One cache with explicit keys solves all three, and it is the library the ecosystem actually uses | Redux or Zustand (client-state tools solving a cache problem), SWR (smaller mutation and invalidation story), another hand-rolled cache (all of the cost, none of the ecosystem), keeping `useEffect` (the duplication this phase exists to remove) |
| 57 | `AuthProvider` keeps the authentication lifecycle (Phase 7) | Who is signed in is not ordinary cached data: it decides routing, it must be cleared instantly on a `401`, and login and logout are explicit lifecycle events rather than a stale-time. The QueryClient is created inside the provider so a `401` can call `clearUser`, and the route guard does the redirect | Moving `/auth/me` into TanStack Query (two owners of the same fact, and a cache eviction would silently sign the user out), duplicating the user in both places |
| 58 | Centralized query-key factories, no keys written inline (Phase 7) | Invalidation is only correct if two places agree on the exact key. One file gives every key one definition, makes the prefix relationships visible, and turns a typo into a compile error instead of a screen that silently never refreshes | Inline key arrays per component (drift, silent stale screens), a string-based key convention (no type safety) |
| 59 | No automatic query retry; a visible "Try again" instead (Phase 7) | `401`, `403` and `404` are correct answers, not flakiness — retrying them hides the reason and delays the error screen. Letting the user retry is honest, keeps tests deterministic and never produces a burst of doomed requests | Retrying everything a few times (slow, confusing errors, noisy tests), retrying only 5xx (extra rule for a case a button already covers) |
| 60 | One workspace dashboard endpoint instead of many small requests (Phase 7) | The overview needs eleven numbers, two distributions and two short lists. Six client requests would arrive at six moments and describe six different states; one aggregation answers a consistent snapshot, computed with `count`/`groupBy` in PostgreSQL and without sending a single issue description | Composing the dashboard from the existing list endpoints (inconsistent snapshot, N+1 over the network), counting in the browser (downloads every issue), a materialized summary table (a second copy to keep in sync) |
| 61 | Overdue is decided by the server clock (Phase 7) | The comparison `dueDate < now` must mean the same thing for everybody. A date sent by the browser can be wrong or forged, so the count would differ per machine. The server returns `generatedAt` with the response, and the client only formats timestamps for display | Comparing in the browser (per-machine truth, trivially forged), storing a timezone per user (a feature nobody asked for), adding a timezone library (ISO strings and `toLocaleString` are enough) |
| 62 | No UI component library and no charting package (Phase 7) | Five status counts are five rows with a CSS bar. A component framework would decide the visual identity that Phase 9 exists to decide, and a chart library would add a large dependency for a bar that `width: %` already draws — with worse accessibility than a labelled number | Material UI / Chakra / shadcn (a design system for an unstyled MVP), Recharts or Chart.js (a heavy dependency for five numbers) |
| 63 | Shared loading, empty and error states instead of blank screens (Phase 7) | Every server-backed screen has the same four outcomes. Three shared components mean one place to improve the wording, and no page can forget an empty state or show nothing while it waits. `ErrorState` reads the HTTP status, so `403` and `404` explain themselves and offer no pointless retry | A spinner per page (repeated and inconsistent), rendering `null` while loading (a screen that looks broken), one generic "Error" string (tells the user nothing) |
| 64 | No last-selected workspace stored in the browser (Phase 7) | The URL already says which workspace is open, and it survives a reload and a shared link. A remembered id would be a second, staler source of truth that has to be re-validated against the membership list on every start, for the sake of skipping one click | Storing the workspace id in localStorage (stale, needs revalidation, can point at a workspace the user was removed from), storing the whole workspace object (the same problem plus duplicated server data) |
| 65 | Final visual design still deferred to Phase 9 (Phase 7) | Phase 7 is about structure: which page exists, where data comes from, and how loading, permission and error states behave. The CSS added here is layout only — one breakpoint, wrapping cards, a scrolling board — so the branding decisions are made once, later, against a finished information architecture | Designing the final UI now (redoing it after the structure moves), leaving the shell unstyled (unusable on a phone, which is a structural failure rather than a cosmetic one) |
